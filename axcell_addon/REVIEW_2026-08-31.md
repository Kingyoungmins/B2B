## 1. 잘 되어 있는 것 (되돌리지 말 것)

이식하면서 의도적으로 손본 것들입니다. 다음 전달분을 받을 때 원본으로 덮어쓰면 되살아납니다.

- `_addon_scheduler_dispatch` 의 **Origin 가드와 예외 경계가 본문을 읽기 전에** 있습니다.
  기존 `local-keys`/`log-sync` 와 같은 자리입니다.
- `launch_b2b.spec` 에 `datas` 와 `hiddenimports` 가 **둘 다** 들어갔습니다.
  하나만 빠져도 프로즌 빌드에서 import 가 죽습니다.
- 텔레메트리 초기화가 `launch_b2b.py` 가 아니라 `start_runtime_maintenance_threads()` 에 있습니다 —
  네이티브 호스트가 소스 모드에서 `serve_b2b.py` 를 직접 띄우는 경로에서도 초기화가 됩니다.
  (교훈 `frozen-startup-code-entrypoint` 와 같은 함정을 피한 것)
- `run_full_pipeline_single_instance` 는 예외를 던지거나 `ok:True` 만 돌려주므로,
  성공/실패 텔레메트리 분기가 실제와 일치합니다.
- `safe_component` 와 `delete_schedule` 의 `resolve()/parents` 검사로 경로 탈출이 막힙니다.

## 2. 새로 확인한 것 (기존 §3 에 없던 것)

고칠 때 여기부터 보시면 됩니다.

### (1) 예전 스케줄의 AX-Cell 교체가 화면에서 막힌다 — 서버는 허용
`scripts/scheduler.js:1278`

`schedule.json` 에 문서 기록이 없는 예전 스케줄(`prevDocs` 가 빈 배열)에서 AX-Cell 을 바꾸려 하면
클라가 "필요한 문서가 다르다" 로 무조건 거절합니다. 빈 배열과 새 문서 목록은 길이부터 다르기 때문입니다.

서버(`b2b_scheduler.py:605`)는 `if prev_docs and ...` 라 **비어 있으면 검사를 건너뛰고 통과**시킵니다.
같은 판정을 두 곳에서 다르게 하고 있고, 더 엄격한 쪽이 화면입니다.

```
클라: prev(0개) != docs(3개)  → 거절
서버: prev_docs 가 비었으므로 검사 안 함 → 통과
```

### (2) 공유하는 AX-Trace 를 지운다
`scripts/scheduler.js:868`

문서 A 의 AX-Trace 를 교체할 때, 같은 파일을 문서 B 도 쓰고 있으면 그 파일이 삭제됩니다.
B 는 없는 파일을 가리킨 채 남습니다.

### (3) 문서가 0개인 스킬은 영원히 등록 불가
`scripts/scheduler.js:269`

문서를 하나도 못 뽑아낸 스킬은 "문서 0개에 …연결되지 않았습니다" 에서 잠깁니다.
빠져나갈 길이 없습니다(문서를 붙일 수도, 그냥 진행할 수도 없음).

### (4) 파일명이 같으면 서로 덮어쓴다
`scripts/scheduler.js:632`

AX-Cell 과 AX-Trace 의 파일명이 같으면 한쪽이 다른 쪽을 덮어씁니다.
매니페스트에는 둘 다 있는 것으로 남아 목록과 실제가 어긋납니다.

### (5) 등록 실패 시 껍데기 폴더가 남는다
`b2b_scheduler.py:237`

여러 파일 중 뒤쪽 하나가 거부되거나 디코딩에 실패하면,
`cron.txt` 도 `schedule.json` 도 없는 ESTB 폴더만 남습니다.

### 재현 확인한 것 (추정 아님)

두 건은 실제로 돌려 확인했습니다.

- **`once` → daily 전환**: 1회 스케줄을 만든 뒤 `/api/scheduler/update` 로 시간만 고치면
  날짜가 사라져 매일 반복이 됩니다.
- **요약 문장 불일치**: `update_schedule` 이 `cron.txt` 만 쓰고 `schedule.json` 의
  `summaryWhen` 을 그대로 둡니다.

## 4. 우선순위에 대한 의견

§3 의 보류 결정을 뒤집자는 게 아닙니다. 다만 **§3-1(1회성 → 매일)** 은 다른 항목과 성격이 다릅니다.

나머지는 사용자가 화면에서 바로 알아챕니다(등록이 막히거나, 글자가 이상하거나).
이건 **아무 표시 없이 매일 실행됩니다.** 사용자가 "한 번만" 으로 등록했다고 믿는 동안
실행이 반복되므로, 알아채는 시점이 늦고 그때는 이미 여러 번 돈 뒤입니다.

실행 주체를 붙이기 전이라면 아직 피해가 없으니, **붙이기 전에** 정리하는 편이 좋겠습니다.
