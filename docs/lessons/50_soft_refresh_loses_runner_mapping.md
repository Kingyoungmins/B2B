# 50. 새로고침(작업 유지) 후 스킬 자동 재적용이 "가끔" 안 되던 이유

- 버전: 0.7.2
- 보고: 사용자 실측 2026-08-04 — "새로고침으로 스킬 전체실행 다시시키는거 뭔가 잘 안되는 경우도 있던데"
- 테스트: `test_runs/_test_soft_refresh_runner_mapping.js` (24 checks)
- 레지스트리: `SOFT-REFRESH-RERUN-FAILS`

## 증상

새로고침 버튼(파일·스킬 유지)을 누르면 파일과 스킬은 잘 복원되는데, 이어지는 자동 재적용이
**될 때도 있고 안 될 때도 있었다.** 실패해도 화면엔 토스트 한 줄만 스쳐 지나가 사용자 입장에선
"그냥 안 됨"으로 보였다.

## 왜 "가끔"이었나 — 갈림길은 실행기 사용 여부

- **생성기에서만 쓰다가 새로고침** → 잘 됨
- **실행기에서 다른 달 파일로 돌린 뒤 새로고침** → 실패

즉 재현 조건이 "실행기 파일확인(매핑)을 거쳤는가"였다. 이게 안 보여서 산발적으로 느껴졌다.

## 원인 4중

### ① 실행기 파일 짝(`state.runnerMappings`)이 스냅샷에 없다 ← 핵심

소프트 리프레시는 `sessionStorage` 스냅샷 + `location.reload()` 구조라, **스냅샷에 안 담긴 상태는
전부 사라진다.** `runnerMappings`(스킬이 찾는 파일 ↔ 실제 업로드 파일의 짝)는 담기지 않았다.

그 결과 4월 스킬을 5월 파일에 매핑해 돌리던 세션이 새로고침되면, 자동 재적용은 스킬에 적힌
**4월 파일명 그대로** 실행돼 "워크북이 열려 있지 않습니다"로 죽는다. 부수적으로 실행기 전체실행
첫 클릭도 실행 대신 파일확인 패널만 다시 열렸다.

### ② 자동 재적용이 매핑 래퍼를 안 거친다

실행기 버튼 경로는 `beginMappedPipelineRun()` 으로 파이프라인을 매핑본으로 갈아끼운 뒤 실행하는데,
`restoreSoftRefreshSnapshot` 의 자동 재적용은 `runPipelineWithAutoRepair` 를 **맨몸으로** 호출했다.
①을 고쳐 매핑을 되살려도 여기서 안 쓰면 무의미하다 — 둘은 같이 고쳐야 한다.

### ③ 실패가 조용하다

실패 처리가 `toast(..., "error")` 한 줄이었다. 표준 오류 카드가 아니라 원인도, [에러 복구 시도]
같은 후속 버튼도 없었다. 게다가 복원된 스킬은 `trustedStatic: true` 라 런타임 자동복구도 스킵된다
— 즉 **아무도 안 고쳐주는데 알려주지도 않는** 조합이었다.

### ④ `b2bJustReset` 표식이 소비되지 않는다

`softRefreshApp` 이 리로드 직전에 심는 "첫 미러 빈화면 자가복구" 표식을 복원 경로가 소비하지 않아,
나중에 세션을 확보하는 시점(하필 전체실행 도중일 수 있음)에 `maybeAutoReapplyAfterRecover` 가
겹쳐 발화했다. 적용 표시가 풀리거나 값이 어긋나는 산발 증상의 원인.

## 수정 (`scripts/soft-refresh.js`)

1. `collectSoftRefreshSnapshot` 에 `runnerMappings` / `runnerMappingChecked` /
   **"지금 계산한"** `runnerMappingSignature` 저장.
   - `state.runnerMappingSignature` 를 그대로 쓰지 않는다 — 이 값은 지연 갱신이라 낡을 수 있고,
     낡은 시그니처를 담으면 복원 때 비교가 무의미해진다.
2. `restoreSoftRefreshSnapshot` 은 **미러 재오픈 뒤** 시그니처가 현재와 일치할 때만 매핑 복원.
   - 불일치(파일이 실제로 달라짐)면 억지로 씌우지 않고 평소처럼 사용자가 파일확인을 하게 둔다.
   - 복원 직후 `state.runnerMappingSignature = curSig` 로 **재-앵커**한다. 이걸 빼면 다음
     `runnerResetMappingIfSourceChanged()`(실행기 진입 등)가 방금 복원한 매핑을 즉시 지운다.
3. 자동 재적용을 `beginMappedPipelineRun()` 으로 감싸고 `finally` 에서 `restore()`.
4. `setGeneratorRunLoading(true/false)` 로 화면 잠금 — 복원 중 사용자가 '전체 실행'을 또 눌러
   같은 라이브 세션에 2중 실행되는 것 방지.
5. 실패는 `reportPipelineError(err)` 로 표준 오류 카드 승격(실패 시에만 토스트 폴백).
6. `sessionStorage.removeItem("b2bJustReset")` 을 복원 완료 시점에 호출.

## 교훈

- **리로드 기반 복원은 "스냅샷에 없는 건 없는 것"이다.** 기능을 추가하며 새 `state` 필드를 만들면
  소프트 리프레시 스냅샷도 같이 늘려야 한다. 안 늘리면 그 기능을 쓴 세션에서만 조용히 깨진다.
- **"가끔 안 됨"은 대개 갈림길이 안 보이는 것이다.** 여기선 "실행기 매핑을 거쳤나"가 갈림길이었다.
- **경로마다 다른 래퍼를 쓰면 갈린다.** 실행기 버튼은 `beginMappedPipelineRun` 을 쓰는데
  자동 재적용은 안 썼다 — 같은 "전체 적용"인데 계약이 달랐다. 자동 경로는 수동 경로와 **같은
  래퍼**를 태워야 한다.
- **표식(flag)은 심은 쪽이 소비 지점도 정해야 한다.** `b2bJustReset` 처럼 여러 경로가 공유하는
  표식은 "누가 언제 지우는가"가 없으면 엉뚱한 타이밍에 터진다.
- 자동으로 뭘 해주는 기능일수록 **실패를 크게 알려야 한다.** 조용한 실패 + 자동복구 스킵
  (`trustedStatic`) 조합은 사용자에게 '프로그램이 이상함'으로만 남는다.
