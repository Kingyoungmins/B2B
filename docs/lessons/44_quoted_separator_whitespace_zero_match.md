# 44. 따옴표 구분자 `' : '` 리터럴 매칭 → 전량 빈값인데 "적용됨" (한화테크윈 DSMC)

## 증상
- "U:U 에는 Q:Q 에서 ' : ' 뒤에 있는 숫자 모두를 기입해줘" 스텝이 "적용됨"으로 끝나는데 U열이 전부 빈칸.
- 같은 표현의 "' : ' 앞 숫자 → T:T" 스텝(11)은 정상 동작. 사용자가 3번 재시도(스텝 12·13·14)했지만
  매번 동일 코드가 재생성돼 결과 동일 — 중복 스텝만 쌓임.

## 원인
1. **구분자 리터럴 과신** — 생성 코드가 요청문의 `' : '`(공백 포함)를 그대로 `if ' : ' in s:` 매칭.
   실제 Q열(통화시간) 값은 `03:20.0`처럼 공백 없는 `:` — 32,602행 전수 스캔 결과 `' : '` 포함 0행,
   `:` 포함 2,494행. 전 행이 else 로 빠져 `[None]`만 기록.
   T열 스텝은 같은 요청 표현인데 모델이 그때는 `if ':' in s:`(공백 무시)로 생성 — 비일관(복불복).
2. **조용한 성공** — 전량 None 쓰기도 저널에 기록돼 `ctx._changed()` True → 무변경 게이트(SBAGENT-209)
   미발동, 예외 없음 → "적용됨". 결과가 논리적으로 비었다는 신호가 어디에도 없었음.
- 참고: 생성 코드에 `import re` 없이 `re.findall` 사용 — 샌드박스가 `re` 를 주입하므로 무해(오진 주의).

## 수정 (0.6.1/0.6.2 동시)
- file-schema.js "값 매칭" 섹션(Python·VBA 양쪽): **따옴표 안 구분자의 주변 공백은 표기 변형** —
  공백 포함 리터럴 매칭 금지, `s.split(':')`+`.strip()` / `Split(s,":")`+`Trim$` 로 공백 무시 매칭.
  ('써넣을 값'은 기존 리터럴 규칙 그대로 — 두 규칙 충돌 없게 단서 명시)
- serve_b2b.py: `_shared` 에 `write_cells_total/nonempty` 집계(ctx.write), `_exec_python_com_skill`
  성공 마무리에서 total>0 && nonempty==0 이면 `summary.emptyWrites=True` + `warning` 문구
  (의도적 비우기 가능성 때문에 실패 아닌 경고. trace: `python_com.all_empty_writes`).
- pipeline.js 라이브 적용 성공 핸들러: `data.emptyWrites` 면 상태 "적용됨(값 0건)" + 경고 토스트.
  components.css `.toast.warning`(amber) 추가.

## 후속 결정 (같은 날)
- 프롬프트 규칙만으로 재발("무조건 공백 무시"는 기존 "따옴표는 리터럴" 규칙과 충돌해 복불복 지속).
- 사용자 결정: **모호하면 물어봐라**. clarify verifier 에 데이터 근거 결정형 검출 추가
  (chat-ui.js `_clarifySeparatorWhitespaceQuestion`): 요청의 따옴표 토큰(공백+짧은 기호 구분자)이
  실제 aoa 셀 값에 그 형태로는 없고 공백 제거형만 있으면 → "실제 데이터는 '03:20.0'처럼 공백 없음.
  공백 무시할까요, 공백 포함만 매칭할까요?" 되묻기. @범위 멘션 요청은 vague 게이트를 통과해버리므로
  이 결정형 경로가 유일한 검출 지점. 값 리터럴('시내호')·공백 없는 구분자·공백형 실존 케이스는 침묵.
- 생성 규칙엔 "[사용자 보충 설명]으로 정한 답 최우선" 단서 추가(되물은 답이 리터럴 규칙을 이김).
- 되묻기 적용 후 2차 오답: `re.findall(r'\d+')` 가 `03:20.0` 의 ':' 뒤 `20.0` 을 `'20','0'` 으로 쪼개
  U열에 "20, 0" 기입. → "숫자/금액" 섹션에 소수점 보존 규칙 추가(Python: `\d+(?:\.\d+)?` 기본,
  매칭 1개면 나열 말고 값 하나로 / VBA: 조각 통째 또는 Val()). 
- 3차 재발: 소수점 규칙을 프롬프트에 넣었는데도 모델이 또 `findall(r'\d+')`+콤마 join 생성
  (앱 미재시작으로 규칙 미탑재였을 가능성도 있으나 어느 쪽이든 프롬프트는 보장이 아님).
  → **정적 게이트로 승격**: 클라 `decimalSplitNumberExtractFailures`(chat-ui.js, commonFailures 재생성
  루프) + 서버 `_python_com_static_check` 동일 검사. '연속 숫자만 findall' AND '콤마 join' 둘 다 있을
  때만 차단해 `''.join`(전화번호 이어붙이기) 등 정상 패턴은 통과. 기존 저장 스텝의 오답 코드도 실행
  시점에 서버 게이트가 명확한 사유로 막는다(조용한 "20, 0" 오답보다 낫다).
- 4차: 게이트 통과 코드가 '20.0' 문자열을 제대로 만들었는데 화면엔 '20.00' — 코드 문제가 아니라
  Excel 이 숫자형 문자열을 숫자로 강제 변환 + **삽입 열이 옆 열의 소수2자리 서식을 상속**해 재표기.
  값 자체는 20.0 으로 정확(표시만 다름). → 프롬프트에 "표기 그대로 기입이 목적이면 쓰기 전에
  `ctx.set_number_format(..., "@")` (VBA: `NumberFormat="@"`), 이후 계산용이면 숫자 유지" 규칙 추가.
  사후 서식은 이미 변환된 값을 못 되돌리므로 반드시 '쓰기 전'.
- 부수 발견: file-schema.js 프롬프트는 템플릿 리터럴이라 `\s` 를 한 번만 쓰면 `s` 로 렌더됨 —
  기존 "정규화 동등 비교 예" 의 `[\s]+` 가 실제론 `[s]+` 로 LLM 에 전달되던 잠복 버그 수정(`\\s`).
  프롬프트에 정규식을 넣을 땐 반드시 `\\` 이중 이스케이프 + 렌더 검증.

## 교훈
- 사용자가 따옴표로 감싼 '구분자/검색어'의 공백까지 리터럴로 믿으면 안 된다. 같은 문구를 모델이
  어떤 날은 정규화하고 어떤 날은 안 하는 비일관이 "T는 되는데 U는 안 됨"류 미스터리를 만든다.
- "실행 성공 ≠ 의미 있는 결과". 쓰기 결과 전량 빈값은 무변경 게이트가 못 잡는 사각지대였다 —
  성공 경로에도 결과 품질 신호(0건 매칭)를 실어야 재시도 루프(동일 문구→동일 실패)를 끊을 수 있다.
