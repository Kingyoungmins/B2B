# 52. 피벗 `header_row` 실패 — 모델 탓이 아니라 우리 API 가 이름을 둘로 쓴 탓

- 버전: 0.7.2
- 제보: 사용자 2026-08-06 — 피벗 생성 스킬이 적용 실패.
  실제 오류 `pivot() got an unexpected keyword argument 'header_row'`
- 테스트: `test_runs/_test_pivot_header_row_com.py` (실제 Excel, 12 checks)
- 레지스트리: `PIVOT-HEADER-ROW-KWARG`

## 무슨 일이 있었나

"헤더명 기준으로 '서비스'별 '할인 후' 합계 피벗을 새 시트에 만들어라" 요청.
생성된 코드가 `ctx.pivot(..., header_row=2)` 였고, 적용이 통째로 실패했다.

AI 도움은 "존재하지 않는 옵션을 준 셈"이라고 정확히 진단했고, 복구 시도는 `ctx.pivot` 을
아예 포기하고 **직접 읽어 손집계하는 코드**로 우회해 성공했다. 결과는 맞았지만,
피벗 헬퍼를 쓰라는 설계 의도(원본 보존·진짜 피벗)에서는 후퇴한 셈이다.

## 진짜 원인 ① — 같은 뜻, 두 이름

| 이름 | 쓰는 헬퍼 |
|---|---|
| `header_row` (단수) | find_header, apply_filter, enable_filter, lookup, dedupe, add_total_row, split_column, move_cols, sum_lookup, match_fill … (13곳) |
| `header_rows` (복수) | **pivot**, native_pivot, filter_to_sheet, _pivot_value_table … (8곳) |

둘 다 뜻은 하나 — **"헤더가 몇 번째 행인지"**. (복수형이지만 '헤더 개수'가 아니다.
`native_pivot` 구현은 `hr = max(1, int(header_rows or 1))` 로 받아 **그 행에서 헤더를 읽는다**.)

단수 쪽이 압도적으로 많으니 그 습관대로 쓰면 피벗에서만 터진다. 실제로 코드베이스는 이미
이 함정을 알고 있었다 — `chat-ui.js` 의 필터 라우팅 힌트에 이런 문장이 박혀 있다:

> "헤더가 2행이면 ctx.find_header(..., header_row=2)와 ctx.filter_to_sheet(..., header_rows=2)를 함께 쓰세요."

**프롬프트로 외우게 하고 있었다는 건, API 가 잘못됐다는 신호였다.** 그리고 그 힌트는
filter_to_sheet 용으로만 있어서 피벗은 무방비였다.

## 진짜 원인 ② — 피벗만 헤더 행을 안 찾아준다

`find_header` 는 예전부터 **지정 행에서 못 찾으면 인접 행도 훑는다**(멀티행/병합 헤더 구제).
그런데 `native_pivot` 은 지정 행만 보고 없으면 그대로 끝냈다:

    피벗 필드 '서비스' 을 헤더에서 찾지 못했습니다

사용자가 "예전에는 헤더 잡았던 것 같은데 이상하네" 라고 한 것의 정체가 이것이다 —
**find_header 는 잡아주고 pivot 은 안 잡아준다.** 같은 앱 안에서 관용도가 달랐다.

## 고친 것

**1) 두 이름을 서로 받아준다 (중앙 1곳)**

`_install_ctx_kwarg_tolerance()` 가 3개 ctx 클래스의 메서드를 훑어, `header_row` /
`header_rows` 를 가진 것만 감싼다. 21개 메서드에 자동 적용 — 개별 수정 21번이 아니다.

**2) 없는 옵션은 '쓸 수 있는 옵션'을 알려주는 오류로**

    pivot() 에 없는 옵션 없는옵션 를 넘겼습니다.
    쓸 수 있는 옵션: after, agg, column, dest_name, group_by, header_row, header_rows, sheet, value

원시 `TypeError` 는 자동복구가 보고 고칠 단서가 없다. 목록을 주면 한 번에 고칠 수 있다.

**3) 피벗도 헤더 행을 자동으로 찾는다**

요청 필드가 지정 행에 없으면 1~10행을 훑어, **전 필드를 담은 행이 '유일'할 때만** 그 행으로
옮긴다. 모호하면 손대지 않고 기존 오류로 간다(조용한 오작동보다 정직한 실패).

**4) 프롬프트 힌트**

피벗 라우팅 힌트에 `header_row` 사용법과 "없는 옵션을 지어내지 말 것"을 명시.

## 교훈

- **같은 개념에 이름이 둘이면, 그건 모델이 아니라 API 의 버그다.** 프롬프트로 외우게 하는
  대응은 그때만 막고 다음 헬퍼에서 또 터진다. 실제로 filter_to_sheet 만 막아 놨더니 pivot 이 터졌다.
- **프롬프트에 "이건 이렇게 부르세요" 를 적고 있다면 설계를 의심하라.** 그 문장이 있다는 건
  자연스럽게 부르면 틀린다는 뜻이다.
- **관용도는 헬퍼마다 다르면 안 된다.** find_header 는 헤더를 찾아주는데 pivot 은 안 찾아주면,
  사용자에겐 "될 때도 있고 안 될 때도 있는 앱"으로 보인다.
- **오류 메시지는 자동복구의 입력이다.** `unexpected keyword argument 'X'` 는 X 가 틀렸다는
  것만 알려주고 무엇이 맞는지는 안 알려준다 — 그래서 복구가 헬퍼를 버리고 손코딩으로 도망갔다.
  쓸 수 있는 옵션을 함께 주면 헬퍼를 유지한 채 고친다.
- **일괄 수정은 개별 수정 N번보다 안전하다.** 21개 메서드를 하나씩 고쳤다면 몇 개는 빠뜨렸을 것이다.
  시그니처를 읽어 자동 적용하면 새로 추가되는 헬퍼도 자동으로 보호된다.
