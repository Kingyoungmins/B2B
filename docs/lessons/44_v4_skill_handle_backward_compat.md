# 44. v4 스킬 자리표(@@FILE_n@@) 하위호환 — 구버전 로드 시 미복원 (2026-07-20, 한전 오류신고)

## 증상 (실측)
0.6.2(v4)가 저장한 스킬 zip을 **v4 미지원 버전(0.6.1 이하)** 에서 열고 전체실행하면:

1. 실행 코드에 자리표가 그대로 남아
   `워크북 '@@FILE_1@@' 이 열려 있지 않습니다. 업로드된 파일명을 그대로 쓰세요.` 로 사망.
2. 파일확인 목록에 **스킬이 실행 중 만드는 중간 시트**(무선간선망/고압모계기/고압자계기)가
   "필요 시트"로 등장(유령 요구). 사용자가 '스킬 기본값'으로 우회해도 1) 때문에 결국 실패.

## 원인
- v4 저장은 코드의 파일명 리터럴을 `@@FILE_n@@` 자리표로 치환하고, 원본 이름은
  `requiredFiles[].{handle,name}` 에 기록한다. **복원은 loadLogic(로드 시)이 담당** — v4 지원
  버전만 이 복원 코드를 가진다.
- 구버전 loadLogic 은 `requiredFiles` 를 모르는 키로 무시 → 자리표가 코드에 잔존.
- 유령 시트의 기제: 생성시트 판정(runnerExtractGeneratedSheetsFromCode / runnerIsGeneratedSheet)은
  (book, sheet) 키로 '만든 시트'와 '읽는 시트'를 조인하는데, 만든 쪽 book 이 `@@FILE_1@@`,
  읽는 쪽 book 이 targetFileId 유래의 실제 파일명이라 **키가 어긋나 생성시트로 인식 못 함** →
  요구 목록에 노출. (v1 원본 zip은 리터럴이라 유령이 안 뜬다 — 실측 대조로 확인.)

## 진단 포인트
- 에러 문구에 `@@FILE_` 이 보이면 = v4 zip 을 자리표 복원 없는 코드가 실행한 것.
  "어느 앱(버전/시점 프론트)이 로드했나"부터 확인. (이번 건: 사용자는 "0.6.1에서"라고 신고했고
  실제로 14:37에 0.6.1 dev 서버가 시작됨 — 저장은 0.6.2, 실행은 0.6.1의 버전 혼용이었다.)
- 재현/회귀: `node diagnostics/_repro_hanjeon_v4_roundtrip.js [logic.json|zip] [--root <버전폴더>]`
  — 실물 아티팩트(`test_data/issue_repro/hanjeon_v4_resaved.logic.json`, `hanjeon_v1_original…`)로
  loadLogic→요구행→매핑 실행코드 E2E. 자리표 잔존/유령 요구 시 exit 1.
  레지스트리: `HANJEON-0720-V4COMPAT` (0.6.1/0.6.2 양쪽 등록).

## 수정
- **0.6.1 백포트(23e100d)**: loadLogic 에서 `data.requiredFiles[].{handle,name}` 으로 자리표만
  원본 이름으로 복원(문자열 치환, runnerReplaceLiteral 재사용). v4 요구 표 자체는 계속 무시
  (기존 코드 추론 유지) — 복원만으로 유령 시트도 함께 사라진다(book 키 재정렬).

## 남는 리스크 / 교훈
- **패치 불가능한 구버전(고객 배포본 0.5.x~0.6.0)은 여전히 v4 zip 을 못 연다.**
  v4 zip 을 고객·타 버전과 공유할 때는 상대 버전을 확인할 것.
- 포맷을 바꾸는 기능(저장측)은 **소비측(로드/러너)과 구버전 동작까지가 완성 범위**다.
  "구버전 zip → 신버전 앱"(전방)만 검증하고 "신버전 zip → 구버전 앱"(후방)을 빼먹으면
  버전 혼용 환경(개발자 병행 테스트, 고객 혼재)에서 즉시 터진다.
- 대안 설계 메모: 자리표는 로드 즉시 복원되므로 **저장 코드에 자리표를 안 박고**(리터럴 유지)
  requiredFiles 표만 자리표 메타를 갖는 방식이면 후방호환이 구조적으로 보장된다. 단 이는
  v4 포맷 설계 변경이라 별도 결정 필요(0.6.2 세션 간 협의).
