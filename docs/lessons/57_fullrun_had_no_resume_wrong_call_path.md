# 57. 실행기 [전체실행]에는 이어실행이 아예 없었다 — 함수만 보고 호출 경로를 안 본 오진

날짜: 2026-08-26 / 버전: 0.8.0

## 증상

사용자가 36스텝 스킬을 실행기에서 돌리다 30단계에서 실패했다. AI 도움으로 30·34단계를
고치고 [전체실행]을 다시 눌렀는데, 앞 단계를 건너뛰기는커녕 **1단계부터 통째로 다시** 돌았다.

로그(`vba_pipeline_trace.jsonl`)가 그대로 말해준다:

```
RUN 2026-08-26T10:23:32  openIds=6 groups=6 totalSteps=36  → 첫 stepIdx 0, 30단계에서 실패(5분 46초)
RUN 2026-08-26T10:29:19  openIds=6 groups=6 totalSteps=36  → 첫 stepIdx 0, 36단계 완주(16분 16초)
```

두 실행 모두 `stepIdx 0` 부터다. 이어실행이 한 번도 안 걸렸다.

## 원인 — 내 오진이 먼저였다

나는 며칠 전 "주석만 바뀐 단계가 이어실행을 깨뜨린다"를 고치면서
`_pipeline_snapshot_key` / `_find_best_pipeline_snapshot` 을 손봤고, 단위 테스트도 통과시켰고,
AI 안내 문구까지 **"[전체실행]을 다시 누르면 앞 단계는 건너뜁니다"** 로 바꿨다.

그런데 그 resume 로직을 쓰는 건 **백그라운드 파이프라인 경로 하나뿐**이었다.

| 화면 동작 | 엔드포인트 | 실행 함수 | 이어실행 |
|---|---|---|---|
| 실행기 [전체실행] | `/api/excel/run-full-pipeline` | `_run_full_pipeline_single_instance_impl` | **없었다** |
| 백그라운드 파이프라인 | `/api/pipeline/start` | `_run_excel_python_pipeline_impl` | 있다 |

확인은 한 줄이면 됐다.

```
sed -n '<runner 함수 범위>' serve_b2b.py | grep -c "resume_from|_find_best_pipeline_snapshot"
→ 0
```

**교훈: 함수 단위로 검증하고 "고쳤다"고 말하지 마라. 사용자가 누르는 버튼에서 그 함수까지
호출이 실제로 닿는지를 먼저 확인해라.** 여기서는 거짓 안내가 제품에 실려 나갔다.
(사용자가 `start_b2b_native.bat` 로 소스 모드 테스트 중이라고 알려주지 않았으면,
"프로즌 exe 가 stale 하다"는 두 번째 오진으로 넘어갈 뻔했다 — 교훈 `stale-frozen-exe-vs-source` 참고.)

## 왜 백그라운드 로직을 그대로 못 쓰나

두 경로는 **상태의 모양**이 다르다.

- 백그라운드: 입력 N개 + 출력 1개. 역할이 고정이라 "출력 워크북 하나"만 스냅샷하면 된다.
- 실행기: 관여 파일 N개를 격리 인스턴스 **하나에 전부** 열고, 그룹(파일) 순서대로 도는
  **평면 스텝열**이다. 어느 스텝이 어느 파일을 바꿀지 고정돼 있지 않다(교차파일 쓰기).

그래서 실행기 전용으로 **경계 스냅샷**을 새로 만들었다.

## 설계 — 경계 스냅샷

**경계 = 스텝과 스텝 사이의 '열린 파일 전부' 상태.** 대상 파일만 저장하면 교차파일 쓰기를
놓쳐 조용히 틀린 결과가 나온다. 이어실행은 틀리느니 안 하는 게 낫다.

비용이 문제였다. 실측 기준선:

```
6개 파일 · 36스텝 · 16분 · 파일 중앙값 12MB
스텝-전 스냅샷(대상 파일 1개)만으로도 60.9초 = 전체의 6%
스텝마다 6개 파일을 다 찍으면 → 약 +37%. 못 쓴다.
```

그래서 **직전 경계 이후 실제로 바뀐 파일만** 찍는다.

1. **대상 파일은 공짜.** 스텝-전 스냅샷(`prestep_*`)을 이미 찍고 있고, 그게 곧 그 시점 상태다.
2. **나머지는 Excel 의 `Saved` 플래그로 판정.** 찍은 뒤 `wb.Saved = True` 로 되돌려 놓으면,
   다음 경계의 `Saved == False` 는 정확히 "그 사이에 바뀌었다"가 된다.
   (`SaveCopyAs` 는 `Saved` 를 안 건드리므로 직접 내려야 한다.)
3. **게이트는 추가 저장이 있을 때만.** 직전 경계가 T ms 걸렸으면 그 9배의 '실행 시간'이
   지나야 다음 경계 → 오버헤드 10% 상한. 새로 찍을 파일이 없으면 게이트를 아예 건너뛴다
   (실패 직전 경계를 놓치지 않기 위해).
4. **한 번도 안 바뀐 파일은 경계에 안 담는다** → 이어실행 때 그 파일만 원본에서 연다.

실측(6스텝 테스트): **경계 4개 · 추가 저장 2회 · 총 35ms.**

## 여기가 제일 깨지기 쉽다 — `Saved` 를 표식으로 쓴 대가

실행 끝의 "변경된 파일만 라이브에 반영" 판정이 `wb.Saved` 를 본다. 우리가 그걸 True 로
되돌리므로 **그대로 두면 바뀐 파일이 동기화에서 통째로 빠진다.**

이어실행이면 더 심하다. 건너뛴 구간에서만 바뀐 파일은 이번 실행에서 한 번도 안 건드리므로
`Saved == True` 다 → 앞 단계 결과 전부가 라이브/출력에서 사라진다.

해결: 우리가 관찰한 dirty 를 `_ever_dirty` 에 모으고(이어실행으로 물려받은 것 포함),
최종 판정을 `(not Saved) or (sid in _ever_dirty)` 합집합으로 한다. `Saved=True` 를 내리기
**전에** 반드시 `_ever_dirty` 에 넣으므로 오늘 동작과 정확히 같은 집합이 된다.

## 안 하는 경우 (일부러)

- **동반 워크북이 열려 있으면 이어실행을 끈다.** 동반본은 원본 파일이 아니라 '지금 라이브
  상태'를 `SaveCopyAs` 한 것이라, 재실행 사이에 같은 상태였는지 지문으로 확인할 방법이 없다.
- **경계를 반쪽만 찍었으면 통째로 버린다.** 파일 하나라도 못 찍으면 그 경계는 없는 것으로 두고,
  이후 경계도 끈다(`Saved` 표식이 어긋났을 수 있다).
- **마지막 스텝 뒤에는 경계를 안 남긴다.** 경계는 스텝 '앞'에서 찍히므로 완주한 실행을 그대로
  다시 누르면 정상적으로 다시 돈다.

## 클라 표시도 같이 이어붙인다

'되돌리기 / Step N까지 적용됨' 목록(`stepSnapshots`)과 교차쓰기 증거(`stepCross`)를 경계에
함께 담아, 이어실행 때 앞에 붙인다. 안 그러면 건너뛴 구간이 비어 화면과 실제가 어긋난다.

## 덤 — 테스트가 옛 트리를 검증하고 있었다

`_test_fullrun_single_instance_live.py` 등 3개가 `sys.path.insert(0, ...B2B_ver0.6.1)` 로
**옛 버전을 import** 하고 있었다. 지금 트리를 고쳐도 통과/실패가 안 바뀌는 테스트였다.
`Path(__file__).resolve().parent.parent` 로 바꿨다. 고정 경로는 이렇게 조용히 죽는다.

## 재발 방지 — 사람 기억이 아니라 명령 한 줄로

`tools/callpath/trace.py` 를 만들었다. 버튼 → 엔드포인트 → 실제 실행 함수를 기계가 따라간다.

```
python tools/callpath/trace.py --assert "runner-run-btn -> _run_full_pipeline_single_instance_impl"
  OK  runner-run-btn → /api/excel/run-full-pipeline → handle_excel_run_full_pipeline
      → run_full_pipeline_single_instance → _run_full_pipeline_single_instance_impl

python tools/callpath/trace.py --assert "runner-run-btn -> _find_best_pipeline_snapshot"
  실패  경로가 없다.        ← 내가 했던 거짓 주장. 이제 exit 1 로 걸린다.
```

만들면서 두 함정을 실제로 밟았다. 둘 다 "도구가 조용히 틀리는" 종류다.

1. **함수를 '넘기는' 것도 실행이다.** `run_full_pipeline_single_instance()` 는
   `excel_call(_run_..._impl, ...)` 로 실행한다. Call 노드만 보면 이 간선이 통째로 빠져
   "어디서도 안 닿는다"는 **거짓 음성**이 난다 → Name 참조도 간선으로 센다.

2. **이름으로 노드를 합치면 안 된다.** `worker` 는 4곳(Excel 큐 펌프 / PPTX 렌더러 /
   백엔드 파이프라인 핸들러 / VBA 디버그 억제기)에서 정의되고,
   `run_backend_pipeline_payload` 는 모듈에 두 번 정의된다(뒤엣것이 이긴다).
   이름으로 합치자 `전체실행 버튼 → capture-copypaste → excel_call → worker → (아무 함수)
   → 백그라운드 resume` 이라는 없는 경로가 생겼고, **도구가 내 거짓 주장을 OK 라고 했다.**
   도구가 거짓을 세탁하면 없느니만 못하다 → 이름이 아니라 **정의 위치(스코프)** 로 해석하게
   다시 썼다(가장 가까운 조상 스코프 → 없으면 모듈 최상위의 마지막 정의).

그 "OK 라고 했던" 케이스 자체를 `test_runs/_test_callpath_trace.py` [2] 에 회귀로 박았다.
