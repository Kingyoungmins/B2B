# 51. 새로고침 후 전 스텝 재실행 → '적용 끝난 사본'으로 즉시 복원

- 버전: 0.7.2
- 발단: 사용자 질문 2026-08-04 — "새로고침 누르면 처음부터 전체실행하잖아? 어차피 스냅샷은 다
  존재할테니까 마지막 스텝 기준 스냅샷만 보여주면 되는거아님?" → "아닌가 엑셀도 다시 리로드해서
  파일이 바뀌나?"
- 테스트: `_test_live_final_snapshot.js`(26) / `_test_live_final_snapshot_backend.py`(22) /
  `_test_live_final_snapshot_com.py`(12, 실제 Excel)
- 레지스트리: `SOFT-REFRESH-INSTANT-RESTORE`

## 왜 원래는 다시 돌려야 했나

사용자의 두 번째 질문이 정답이었다. **파일이 바뀌는 게 아니라, 안 바뀌어서** 다시 돌린 것이다.

라이브 Excel 은 원본이 아니라 **작업 복사본**이고, 스킬 적용 결과는 **메모리에만** 있다. 닫을 때
`SaveChanges=False` 로 일부러 저장하지 않는다(그래야 강제 종료해도 원본이 안 망가진다). 그래서
새로고침으로 Excel 을 죽이면 적용 결과가 같이 증발하고, 다시 연 창은 원본 상태다.

## "스냅샷"이 세 가지 다른 뜻으로 쓰이고 있었다

이 이름 충돌이 논의를 헷갈리게 했다. 코드를 읽을 때 반드시 구분할 것:

| 이름 | 정체 | 새로고침 후 |
|---|---|---|
| `PIPELINE_STEP_SNAPSHOTS` | 디스크 xlsx 사본 — Python 격리 파이프라인의 스텝 prefix 이어달리기 캐시 | 살아남음 |
| `session["snapshots"]` | 시트 값 배열(미리보기·변경감지용), 메모리 | 소멸 |
| soft-refresh 스냅샷 | sessionStorage(파일 workbookId + 스킬 json) | 살아남음 |
| **`LIVE_FINAL_SNAPSHOTS`** (신규) | 엔진 무관 '파일 1개의 최종 상태' 사본 | 살아남음 |

## VBA 는 사본이 없었다 — 없어도 되는 설계라서

- **Python 격리 경로**: 파일을 열고 닫으며 도니, 김에 `SaveCopyAs` 로 사본을 남기고 다음엔 그 지점부터
- **VBA 라이브 경로**: `run_vba_pipeline_on_session(..., reset=True)` — **원본부터 코드를 다시 실행**하는
  게 기본. 되돌리기도 같은 방식이라 애초에 중간 사본이 필요 없다

즉 VBA 쪽이 빠진 게 아니라 복원 전략이 다른 것이다. 다만 새로고침 복원에는 사본이 필요했다.

## 비용이 0이었던 이유 (처음 추정은 틀렸다)

처음엔 "VBA 에 사본을 뜨면 매 실행마다 `SaveCopyAs` 가 붙어 평소가 느려진다"고 판단했다. **틀렸다.**

`_run_full_pipeline_single_instance_impl` 은 결과를 라이브에 반영할 때 이미
`fwb.SaveCopyAs(rpath)` 로 **디스크에 쓰고 있었고**, 끝에서 `shutil.rmtree(work)` 로 **버리고 있었다.**
버리는 대신 옮겨 담기만 하면 된다 → 추가 COM 저장 0회.

Python 쪽도 마찬가지로 이미 저장된 스텝 스냅샷 파일을 **가리키기만** 한다(`link` 모드).

## 구현

- **키** = `sha256(원본 파일 지문 + 클라가 준 stateSig)`. 백엔드는 stateSig 를 해석하지 않는다 —
  저장 때와 조회 때 클라가 같은 규칙으로 만들기만 하면 된다.
  - 원본 지문에 크기·mtime 이 들어가는데 **원본을 저장하지 않으므로** 새로고침 뒤에도 그대로다.
    원본이 실제로 바뀌면(재업로드) 키가 달라져 옛 사본을 안 쓴다.
- **stateSig** = 활성 스텝의 (id, language, targetFileId, 코드) 를 이어 붙여 64비트 해시.
  32비트 하나로는 대량 스텝에서 충돌 확률이 무시 못 하고, **충돌 = 엉뚱한 상태로 복원**이라 위험하다.
- **전체실행일 때만 발행**(`pipelineFullRunStateSig`). 부분/이어실행 결과는 최종 상태가 아니라
  남기면 '덜 적용된 상태'를 최종본으로 착각한다.
- **복원**: `/api/excel/open` 에 `fromStateSig` → 작업복사본을 만들 때 원본 대신 사본을 원료로 쓴다.
  **워크북 레코드의 `path` 는 건드리지 않는다** → 리셋/되돌리기는 그대로 진짜 원본을 찾는다.
- **all-or-nothing**: 관여 파일 전부에 사본이 있을 때만 쓴다. 일부만 쓰면 파일마다 적용 시점이 어긋난다.
- 복원 성공 시 스텝을 `applied`("적용됨")로 표시 + `noteLivePipelineApplied` — 안 하면 전부 '보류'로
  보여 사용자가 또 실행을 누른다.

## 교훈

- **"어차피 있잖아"를 의심하라.** 여기선 "스냅샷"이라는 같은 이름이 4개의 다른 것을 가리켰고, 그중
  실제로 화면을 되살릴 수 있는 건 하나도 없었다(그래서 새로 만들어야 했다).
- **비용 추정 전에 그 경로가 이미 뭘 하고 있는지 읽어라.** "SaveCopyAs 비용이 붙는다"는 추정은,
  이미 SaveCopyAs 해서 **버리고 있다**는 사실 앞에서 무너졌다. 되돌아보면 10줄 읽으면 알 수 있었다.
- **엔진마다 복원 전략이 다르면 대칭성을 가정하지 마라.** VBA=재실행, Python=파일. 어느 쪽도
  틀리지 않았지만, 둘을 같은 기능으로 묶으려면 공통 계층(엔진 무관 최종상태 사본)이 필요했다.
- **부가기능은 절대 본 기능을 깨면 안 된다.** 사본 저장은 전 구간 예외를 삼키고, 조회 실패·정리로
  인한 소실·서명 불일치는 전부 '평소대로 전체 재실행'으로 떨어진다.
- **COM 테스트는 스레드 소유권을 맞춰야 한다.** `open_excel_session` 이 만든 워크북은 Excel 워커
  스레드 소유라 메인 스레드에서 읽으면 마샬링 오류가 나고, 테스트가 직접 만든 세션은 그 반대다.
  같은 테스트 안에 두 종류가 섞이면 읽는 경로를 각각 맞춰야 한다.
