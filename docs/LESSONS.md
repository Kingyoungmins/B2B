## 1. 배포 순서 함정 — 파일만 복사하고 서버를 안 껐다 (가장 중요)

### 사례

2026-09-03. 세션 상세 API(`/v1/admin/session/detail`)를 만들고 `collector.py` 를 보안망에
복사했습니다. 그런데 대시보드에서 실행 목록의 한 줄을 펼치면 **"상세를 불러오지 못했습니다"**
만 떴습니다. 코드는 분명히 서버에 있고, 로컬에서는 테스트가 전부 통과했습니다.

프록시 로그를 보니 응답이 **404** 였습니다. 서버를 **재시작**하니 바로 200 OK.

### 원인

파이썬은 **프로세스가 시작할 때 파일을 읽어 메모리에 올립니다.** 파일을 덮어써도 **이미 돌고
있는 프로세스는 옛 코드를 그대로 실행**합니다. 새로 추가한 라우트는 옛 프로세스의 라우팅
테이블에 없으니 FastAPI 가 404 를 줍니다 — "코드가 없다"가 아니라 "그 프로세스는 그 길을
모른다" 입니다.

여기에 두 가지가 겹쳐 착각을 키웠습니다.

- `version.txt` 는 **요청마다 다시 읽기** 때문에 "이 서버는 파일만 고치면 된다"는 인상이
  있었습니다. 그건 `version.txt` 에만 해당합니다.
- `start_log_server.bat` 은 4단계에서 `/v1/logs/health` 를 찔러 보고 **이미 떠 있으면 그 서버를
  그대로 쓰고 관리자 화면만 엽니다.** 그래서 배치 파일을 다시 두 번 클릭해도 새 코드가 안
  올라갑니다("[알림] 수집 서버가 이미 떠 있습니다. 관리자 화면만 엽니다.").

### 대응

- **`main.py` / `collector.py` / `drm.py` 를 바꿨으면 반드시 프로세스를 다시 띄운다.**
  순서와 검증 명령은 [DEPLOY.md](DEPLOY.md) 에 체크리스트로 있습니다.
- 배포 확인은 "파일이 있는가" 가 아니라 **새 엔드포인트를 직접 한 번 부르는 것**으로 합니다.
  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" \
    "http://127.0.0.1:8100/v1/admin/session/detail?user=없는사용자&session=없는세션"
  # 404 라도 그건 '세션이 없다' 는 404 다. 라우트가 없으면 본문이 {"detail":"Not Found"} 로 온다 —
  # 본문까지 보고 구분하거나, 실제 세션 값으로 200 을 확인하는 편이 확실하다.
  ```
- 개발 PC 에서는 배치 파일을 다시 누르기 전에 **먼저 서버 창을 닫습니다**(Ctrl+C).

### 같은 계열 함정 — 여러 줄 version.txt 는 main.py 가 먼저다

`version.txt` 를 여러 줄(허용 목록)로 바꾸면서 **`main.py` 를 안 올리면** 구버전 `main.py` 가
**첫 줄만** 읽어 엉뚱한 버전과 비교합니다. 그러면 멀쩡한 최신 앱에도 교체 안내가 뜨거나, 반대로
막아야 할 버전이 통과합니다.

→ **`main.py` 를 먼저(또는 같이) 올리고 재시작한 다음** `version.txt` 를 여러 줄로 바꿉니다.
확인은 `curl "…/v1/version"` 에 `allowed` 배열이 오는지로 합니다. 구버전 `main.py` 는 `allowed`
필드가 아예 없습니다.

## 2. 집계 캐시 버전(`v`) 을 안 올려 옛 숫자가 계속 나왔다

### 사례

활성 시간의 자리비움 기준을 5분에서 10분으로 바꿨는데 대시보드 숫자가 그대로였습니다.

### 원인

세션 집계는 `<log-root>/.agg_cache/<날짜>/<사용자>/<세션>.json` 에 저장됩니다. 캐시를 쓸지
말지는 두 가지로 판단합니다.

```python
if cached.get("sig") == sig and cached.get("v") == 5:
    return cached["agg"], True
```

- `sig` = 그 세션 `logs/*.jsonl` 의 `이름:크기:mtime` — **로그가 바뀌었는지**만 봅니다.
- `v` = **집계 규칙의 버전** — 코드가 바뀌었는지는 이 숫자로만 알 수 있습니다.

닫힌 세션은 로그가 더 이상 바뀌지 않으므로 `sig` 는 영원히 같습니다. 즉 `v` 를 안 올리면
**계산식을 어떻게 바꿔도 옛 결과가 그대로 서빙됩니다.**

### 대응

- `_scan_session_events` 의 집계 규칙을 건드렸다면 `_session_events` 의 `v` 를 **반드시**
  올린다. 지금까지의 이력(코드 주석에도 남겨 두었습니다):

  | v | 무엇이 바뀌었나 |
  |---|---|
  | v2 | `tokens` 추가 (2026-09-02) |
  | v3 | `fullRuns` 추가 (2026-09-03) |
  | v4 | `activeMinutes` 추가 (2026-09-08) |
  | **v5** | 자리비움 기준 5분 → 10분 (2026-09-08) |

- 두 군데를 같이 고쳐야 합니다: 캐시를 **읽는** 조건의 `v == 5` 와 캐시를 **쓸** 때의 `"v": 5`.
- 급하면 `<log-root>/.agg_cache` 폴더를 지우면 됩니다(다음 조회 때 다시 만듭니다). 폴더가 크면
  첫 조회가 오래 걸립니다.
- 참고: 캐시 무효화는 `*.jsonl` 만 봅니다. `*.log` 만 바뀐 경우 재스캔하지 않는데, 집계 대상이
  `*.jsonl` 뿐이라 결과가 같아서 의도한 동작입니다.

## 3. 하위 호환 — 새 필드는 "항상 없을 수 있다"

### 사례

조직 정보(`extra.org`)를 추가한 뒤, 이미 쌓여 있던 세션과 구버전 앱이 보낸 세션에서
`displayName`/`team`/`orgPath` 가 없어 대시보드가 깨질 수 있었습니다.

### 원인

수집 서버는 **여러 버전의 앱을 동시에 상대합니다.** 사내 배포는 단계적으로 이뤄지고, 이미
디스크에 쌓인 옛 세션은 절대 바뀌지 않습니다. 그래서 새로 만든 필드는 **처음부터 없는 값**이
정상 입력값입니다.

### 대응 (코드에 이미 적용된 방식)

- 읽을 때 항상 기본값을 준다.
  ```python
  org = (meta.get("extra") or {}).get("org") or {}
  "team": str(org.get("team") or ""),
  ```
  → 없으면 **빈 문자열**로 나가고 대시보드가 `-` 로 그립니다. 화면은 안 깨집니다.
- 집계처럼 실패할 수 있는 계산은 감싸고 실패 시 `null` 을 준다.
  ```python
  try:
      agg, _hit = _session_events(d, u, sdir)
      row["tokens"] = {...}
  except Exception:
      row["tokens"] = None       # 목록은 그대로 나가고 대시보드는 '-' 로 표시
  ```
- `session/start` 가 유실돼도 자료는 버리지 않는다(`_resolve_or_recover` → `recovered:true`).
  '받은 건 일단 남긴다' 가 수집기의 유일한 원칙입니다.
- 반대 방향도 지킨다: 새 서버가 **구버전 앱**을 깨뜨리지 않게, 버전 응답의 `version`/
  `normalized` 는 허용 목록의 최댓값으로 계속 채웁니다(구버전 앱은 그 필드 하나만 봅니다).

## 4. 개인정보 — logs/ 는 절대 커밋하지 않는다

### 사례

`logs/` 에는 사내 사용자의 **실명**(`displayName`), **마당 아이디**(`madangId`), **조직 경로**
(`orgPath`: LG유플러스 > CTO > … > 팀), PC 이름, 실행 시각, 그리고 업무 로그 원문이 들어 있습니다.
`.agg_cache` 에도 사용자 폴더 이름이 경로로 들어갑니다.

### 원인

수집기의 목적 자체가 "누가 언제 무엇을 했나"를 남기는 것이라, 저장물은 본질적으로 개인정보입니다.

### 대응

- `.gitignore` 에 `logs/` 와 `.env` 가 있습니다. **이 두 줄을 지우거나 `-f` 로 강제
  add 하지 마세요.**
- 문서·이슈·채팅에 로그 내용을 붙일 때는 이름/아이디/조직을 지우고 붙입니다. 이 저장소의
  문서에 나오는 이름·아이디는 코드 주석에 이미 있는 예시 값입니다.
- 진단 파일(`<log-root>/_diagnostics/`)에는 서버 IP·경로가 들어갑니다. 이것도 같은 취급입니다.
- 응답에 키 값(MIP keyCode)은 어디에도 싣지 않습니다 — `있음/없음` 여부만 알려줍니다.

## 5. 테스트가 날짜에 묶여 있었다 (`test_dashboard_api.py`)

### 사례

2026-09-09 실측: `test_dashboard_api.py` 가 **5건 실패**합니다.

```
FAIL  세션 수  -> {'sessions': 4, ...}      # 2개를 넣었는데 4개로 집계
FAIL  체류 합(42+5분)  -> 46428.6            # 42+5=47 분이어야 하는데 32일치
```

### 원인

서버 버그가 아니라 **테스트가 고정 날짜(`2026-08-24`)를 쓰기 때문**입니다.

- `POST /logs/session/start` 의 요청 모델(`SessionStart`)에는 **`date` 항목이 없습니다.**
  보내도 무시되고 세션 폴더는 항상 **서버의 오늘 날짜**로 만들어집니다.
- 반면 `logs/append`·`logs/file`·`logs/session/end` 는 `date` 를 **봅니다**. 테스트가
  `date:"2026-08-24"` 로 보내니 그 폴더를 못 찾고, `_resolve_or_recover` 가
  `2026-08-24/<user>/<session>` 폴더를 **하나 더** 만듭니다(`recovered:true`).
- 결과적으로 사용자당 폴더가 2개(오늘 + 8/24) → 세션 4개. 오늘 날짜 폴더는 `startedAt` 이
  8/24 인데 `lastSeenAt` 이 오늘이라 체류 시간이 32일로 계산됩니다.

`collector._today` 를 `2026-08-24` 로 바꿔 돌리면 **ALL PASS** 가 나옵니다 — 날짜 의존임을
확인한 방법입니다.

### 대응

- 테스트를 고칠 때는 고정 날짜 대신 **오늘 날짜**를 쓰거나, `session/start` 에도 날짜를
  받게 만들어야 합니다. 어느 쪽이든 앱 동작에 영향이 있으니 지시를 받고 하세요
  (2026-09-09 시점에는 문서로만 남기고 코드는 손대지 않았습니다).
- 자정 넘겨 실행하는 세션은 실제로도 이 경로를 탑니다: 시작은 어제 폴더, 이후 업로드가
  `date` 를 비워 보내면 최근 60개 날짜 폴더를 뒤져 **어제 폴더를 찾아** 이어붙입니다.
  앱이 `date` 를 오늘로 채워 보내면 새 폴더가 생길 수 있습니다.

## 6. 한국어 Windows 콘솔에서 테스트가 UnicodeEncodeError 로 죽었다

### 사례

```
UnicodeEncodeError: 'cp949' codec can't encode character '—' in position 19
```

`test_dashboard_api.py` 와 `test_admin_events.py` 가 첫 `print` 에서 죽습니다.

### 원인

한국어 Windows 의 기본 콘솔 코드페이지는 cp949 라서 `—`(em dash) 같은 글자를 못 찍습니다.
다른 테스트들은 파일 맨 위에서 스스로 맞춰 둡니다.

```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

이 두 파일에만 그 한 줄이 없습니다.

### 대응

```bat
set PYTHONIOENCODING=utf-8
python test_dashboard_api.py
```

또는 `chcp 65001`. 새 테스트를 만들 때는 다른 파일처럼 `sys.stdout.reconfigure(...)` 한 줄을
맨 위에 넣으세요 — 환경변수를 기억해야 하는 테스트는 결국 안 돌아갑니다.

## 7. 점검·진단이 서비스를 죽였다 (서비스가 먼저다)

### 사례

2026-08-27. 게이트웨이가 막힌 상태에서 서버를 띄우면 **90초 넘게 포트가 열리지 않았고**,
플랫폼 헬스체크(`GET /v1/models`)가 실패해 **파드가 계속 재시작**됐습니다.

### 원인

시작 자가진단을 **기동 경로 안**에서 돌렸습니다. TLS 시도마다 제한시간을 다 쓰는데, 그 시간
동안 uvicorn 이 뜨지 못했습니다. 진단하려다 서비스를 죽인 셈입니다.

### 대응

- 점검·진단은 **서버가 응답을 시작한 뒤 5초 후 백그라운드 스레드**에서 돕니다
  (`start_background_checks`). 첫 헬스체크가 지나간 뒤에 무거운 일을 시작합니다.
- `GET /v1/models` 는 **어떤 상태에서도 200**을 유지합니다. `version.txt` 를 못 읽어도
  200 입니다 — 여기서 500 을 내면 "서비스 자체가 죽은 것"으로 오인돼 상위 점검이 전부
  실패로 잡힙니다.
- 부가 기능은 없어도 죽지 않게: `collector.py`·`drm.py` import 실패는 경고만 찍고 버전 확인은
  계속 돕니다. `--log-root` 를 못 만들면 `main.py` 옆 `logs` 로 물러납니다.
- 교훈 한 줄: **점검은 아무리 유용해도 서비스보다 뒤다.**

## 8. "종료 신호"를 믿으면 상태가 고착된다

### 사례

2026-09-02. 대시보드에 거의 **모든 세션이 "수집 중"** 으로 보였습니다.

### 원인

앱을 X 로 닫으면 호스트가 응답 직후 서버 프로세스를 kill 해서 `session/end` 가 유실되는
레이스가 있었습니다(앱 쪽에서 응답 전 전송으로 수정). 하지만 크래시·전원 꺼짐·네트워크
단절은 앞으로도 계속 생기고, 이미 쌓인 세션은 영원히 `closed:false` 입니다.

### 대응

- 서버가 흡수합니다: `lastSeenAt` 이 **600초(10분)** 넘게 없으면 `stale:true`
  → 대시보드가 "종료(추정)" 으로 표시. `stats.openSessions` 에서도 제외합니다.
- 10분은 클라 전송 주기(10~30초)의 넉넉한 배수입니다. 9분은 아직 "수집 중"이라는 것을
  `test_stale_sessions.py` 가 고정합니다.
- 시각을 못 읽으면 `stale` 을 주지 않습니다(함부로 끊김 처리하지 않음). 반대로 시각 기록이
  **아예 없으면** 살아있다고 볼 근거가 없어 `stale:true` 입니다.
- 같은 발상이 체류 시간에도 적용됩니다: `endedAt` 이 없으면 `lastSeenAt` 으로 물러납니다.
  그러지 않으면 강제 종료 세션이 전부 0분으로 사라집니다.

## 9. 집계는 "일부만 보면" 구조적으로 틀린다

### 사례

`/admin/errors` 가 예전에는 로그 파일 **끝 256KB** 만 봤습니다. 큰 세션의 앞부분 오류가 통째로
빠져서, 그 숫자로 '오류율' 을 그리면 항상 과소집계였습니다. `limit` 도 먼저 찾은 것부터 잘라서
정작 최신 오류가 빠졌습니다.

### 원인

성능을 위해 범위를 줄였는데, 그 결과가 **지표**로 쓰이면서 "빠른 오답"이 됐습니다.

### 대응

- 전량 스캔으로 바꾸고, 대신 **세션당 1회 + 캐시**로 성능을 확보했습니다(교훈 2번의 캐시).
- `limit` 은 **정렬 후** 자릅니다.
- 그래도 상한은 필요합니다(파일당 50MB, 세션당 오류 500행). 잘라낸 만큼은 숨기지 않고
  `scanned.skippedBytes` 로 알려줍니다 — **얼마나 못 봤는지가 응답에 보여야** 숫자를 믿을지
  판단할 수 있습니다.

## 10. 경로에 들어가는 값은 전부 세탁 + 한 번 더 확인

### 사례

사용자·세션·파일 이름은 모두 클라이언트가 보낸 문자열입니다. 그대로 폴더 경로에 붙이면
`../../etc` 같은 값으로 서버 아무 곳에나 쓰거나 읽을 수 있습니다.

### 대응

- `safe_part`(폴더), `safe_filename`(파일)로 화이트리스트 세탁 — 한글을 살려 둔 이유는 스킬 zip
  이름이 한글이기 때문입니다.
- 세탁만 믿지 않고 **한 번 더 확인**합니다. `/admin/session/file` 은 세탁 후에도
  `path.parent != (sdir / kind)` 이면 404 를 줍니다.
- `kind` 는 `logs|skills` 화이트리스트, 날짜는 `^\d{4}-\d{2}-\d{2}$` 정규식으로만 받습니다.
- 버전 파일 경로는 **켤 때의 인자로만** 정합니다 — 요청으로 받으면 임의 파일 읽기가 됩니다
  (`test_version_service.py` 가 `path` 파라미터를 무시하는지 고정합니다).
- 이 규칙들은 전부 테스트로 잠가 두었습니다. 세탁 코드를 건드리면 `test_log_collector.py` 와
  `test_session_detail.py` 를 반드시 돌리세요.

## 11. `.env.example` 이 저장소에 없다 (2026-09-09 확인)

### 사례

`git clone` 만 하면 `.env.example` 이 없습니다. 실제 파일은 `__pycache__/.env.example` 에 있고,
`.gitignore` 가 `__pycache__/` 를 제외하므로 **추적되지 않습니다.**

### 원인

파일이 캐시 폴더 안에 들어간 채로 커밋 대상에서 빠졌습니다.

### 대응

- 문서보안을 새로 설정할 때 필요한 키 목록은 [README 의 문서보안 · 설정(.env)](../README.md)
  표에 그대로 적어 두었습니다. 그 표를 보고 `.env` 를 직접 만들면 됩니다(값은 담당자에게).
- 저장소 루트에 값이 빈 `.env.example` 을 추가해 두면 다음 사람이 편합니다 — 다만 **`.env`
  자체는 절대 커밋하지 않습니다.**


## 12. 누적 파일은 세션 소속이 아니다 — 활성시간 > 체류, 전체실행 중복 (2026-09-09)

**사례**: 대시보드에 '활성(추정)'이 '체류'보다 큰 세션이 여럿(전부 +0.8분). 세션 폴더의 `telemetry_preview.jsonl` 을 열어
보니 9/1 부터의 기록이 전부 들어 있었다. 앱 쪽은 이 파일을 세션마다 리셋하지 않고 누적하며, `log_sync` 는 세션 시작마다
오프셋을 0 으로 돌려 매번 처음부터 올린다. 그 안의 오래된 두 기록(49초 간격)이 모든 세션에 +0.8분을 얹었고, 전체실행
횟수는 세션마다 과거분까지 다시 셌다(한 세션에 7건 중 6건이 남의 것). 타임스탬프는 UTC(Z)였다.

**원인**: "세션 폴더에 있는 파일 = 그 세션의 기록"이라는 가정. 누적 파일에는 성립하지 않는다.

**대응**: (1) 누적 파일(`_CUMULATIVE_LOG_FILES`)에만 세션 시간창 필터 (2) UTC 변환 (3) 종료 세션에만 활성≤체류 클램프
(4) 캐시 버전 v6 로 소급 교정. 열린 세션에 클램프를 걸면 활성이 0 으로 잘린다 — 실측으로 한 번 밟았다.
