## 2. 발명이 속하는 기술분야 및 종래 기술

### 2-1. 발명이 속하는 기술분야 및 목적

본 발명은 사무 자동화(Office Automation) 및 인공지능 응용 분야에 속하며, 구체적으로는
(i) 사용자의 자연어 지시를 대규모 언어 모델(LLM)로 스프레드시트 조작 코드(이하 "스킬")로 변환하고,
(ii) 그 스킬을 **실제 설치된 스프레드시트 애플리케이션(Microsoft Excel)의 라이브 인스턴스**에 대해
원본 무손실로 실행·검증하며,
(iii) 검증된 스킬을 **파일명·시트명이 달라진 다음 회차 문서(예: 익월 정산 파일)에 자동 재바인딩하여 재사용**하는
기술에 관한 것이다.

목적: 통신·카드 정산 등 B2B 반복 정산 업무에서, 비개발자인 실무자가 자연어만으로 수십 단계의
엑셀 가공 절차를 1회 작성·검증해 두면, 매월 파일만 바꿔 넣어 무인에 가깝게 재실행할 수 있게 하는 것이다.

### 2-3. 종래기술의 문제점

1. **라이브 애플리케이션 부재**: (나)·(바)류는 서버 샌드박스에서 파일 '사본'을 변환할 뿐, 사용자가 쓰는
   실제 Excel 화면(피벗테이블, 서식, 수식 재계산, 병합 셀 등 네이티브 기능 포함)과 단절된다.
   결과물을 눈으로 검증하려면 다운로드→열기를 반복해야 한다. (사)는 애드인 방식으로 라이브 문서에
   동작하는 예외이나, 아래 2·3·7의 문제 — 절차의 저장·재사용 부재, 실패 시 원본 보호·복구 부재,
   교차파일 횡단 절차 부재 — 는 동일하게 남는다(즉 '라이브'만으로는 본 발명의 과제가 해결되지 않는다).
2. **재사용 불가(1회성) 및 절차 수준 조작 부재**: (가)~(다)·(사)는 지시 1건당 1회 실행이 기본이며,
   "지난달에 했던 그 절차"를 새 파일에 그대로 적용하는 수단이 없다 — 검증된 절차를 스텝 파이프라인
   으로 저장했다가 파일만 바꿔 재실행하는 개념 자체가 부재하다. 절차가 스텝 단위로 구조화되지 않는
   귀결로, **특정 단계만 켜고 끄기(on/off), 단계 단위 되돌리기/다시하기(undo/redo), 실패·수정
   지점부터의 부분 재실행** 같은 절차 수준의 조작도 원천적으로 불가능하다(셀 편집 수준의 실행취소와는
   구별되는, 파이프라인 단계 단위의 조작을 말한다). (마)의 매크로는 기록 시점의 파일명·시트명
   리터럴에 고정되어 파일명이 "4월→5월"로만 바뀌어도 실패한다.
3. **원본 훼손 위험**: 라이브 애플리케이션을 직접 제어하는 접근(라, 마, 사)은 실행 실패·중단 시 원본
   문서가 중간 상태로 오염되고, 어디까지 적용됐는지 알 수 없어 되돌릴 수 없다.
4. **LLM 코드의 불확실성**: LLM이 생성한 코드는 시트명 착오, API 제약(시트명 31자 제한, CSV 단일
   시트 등) 위반, 성능 문제(과다 셀 읽기)로 실패할 수 있으나, 종래기술은 실패 시 처음부터 재시도하거나
   사용자에게 원인 불명의 오류만 보고한다.
5. **입력 요구의 불투명성**: 저장된 자동화 절차가 "어떤 파일의 어떤 시트"를 요구하는지 기계가 알지
   못해, 새 파일 투입 시 무엇을 무엇에 대응시켜야 하는지 사람이 코드를 읽고 판단해야 한다.
6. **사용자 수작업과 자동화의 단절**: 사용자가 화면에서 직접 한 복사/붙여넣기 같은 조작은 자동화
   절차에 편입되지 않는다. (마)의 기록기는 애플리케이션 전역 이벤트 후킹에 의존해 부정확하고 보안
   제품과 충돌한다.
7. **교차파일(다중 워크북) 작업 미지원**: 정산 실무의 핵심은 "A 파일 시트에서 집계해 B 파일 시트에
   기입", "A의 시트를 B로 통째 복사" 같은 **여러 파일을 횡단하는 작업**인데, (가)~(다)는 단일 문서
   문맥에서만 동작하고 (나)·(바)류도 변환 단위가 파일 1개에 갇히며, (사)도 활성 워크북 문맥 중심으로
   교차파일 동작 여부가 불명하다. 파일 간 참조가 걸린 절차를 저장했다가 "파일 세트"를 통째로 바꿔
   재실행하는 수단은 발명자가 인지하는 어느 것에도 없다.
8. **컴퓨팅 자원·환경 의존**: (가)(다)는 클라우드 구독과 클라우드 저장 문서를 전제하고, (나)는 파일
   전체를 외부 서버에 업로드해야 하며(보안 문제 병발), (바)류는 데이터프레임 전체 적재 방식이라
   대용량(수십만 행)에서 고성능 CPU·대용량 RAM 을 요구한다. 사무 현장의 표준 저사양 PC(4코어급
   CPU, 12GB RAM, HDD)에서 수십 스텝·수십만 행 절차를 완주할 수 있는 구조가 아니다.
9. **파일 포맷·애플리케이션 버전 커버리지 한계**: (나)(바)류는 자체 파서(openpyxl, pandas 등)가
   지원하는 포맷(주로 .xlsx/.csv)에 갇혀, 실무에 흔한 .xls(구버전 바이너리), .xlsb, 확장자 위장
   파일(내용은 HTML/CSV 인데 확장자만 .xls 인 시스템 추출물)을 열지 못하거나 서식·수식·피벗을
   잃는다. 또한 파서 버전과 문서 생성 버전의 어긋남이 사용자 책임으로 남는다. (사)는 기설치 Excel
   을 활용하나 애드인 플랫폼(M365 계열)을 지원하는 Excel 버전·배포 채널에 한정되는 반면, 본 발명은
   COM 자동화가 가능한 데스크톱 Excel 이면 버전·채널 제약 없이 동작한다.

## 3. 발명의 목적 / 효과 (달성하고자 하는 과제)

### 3-1. 본 발명이 어떻게 종래기술의 문제점을 극복하였는지

| 종래 문제 | 본 발명의 해결수단 |
|---|---|
| ① 라이브 부재 | **오버레이 임베딩**: 실제 EXCEL.EXE 창을 자식창화(SetParent)하지 않고 top-level을 유지한 채 스타일 변형(캡션 제거·툴윈도우화)과 무활성 배치(SW_SHOWNA/SWP_NOACTIVATE)로 앱 UI 안에 합성한다. 자식창화 시 셀 클릭·선택 입력이 사멸하는 문제를 회피하면서 네이티브 Excel 전 기능을 그대로 노출한다. (도 1, 구성 300) |
| ② 재사용 불가 | **정적 요구 추출 + 생성물 제외 + 자동 매칭 + 리터럴 재바인딩**: 저장된 스킬의 코드·메타데이터를 정적 분석해 (파일, 시트) 요구 목록을 만들되, 스킬이 실행 중 스스로 만들어내는 시트(추가·개명·복사 산출물)는 변수 대입 추적까지 동원해 요구에서 제외한다. 새 파일들과 5단 점수 사다리(정확→정규화→어간→포함→토큰)로 자동 매칭하고, 실행 직전에만 코드 리터럴을 치환한 '매핑본'을 만들어 실행하며 저장본은 불변으로 유지한다. (도 3, 구성 400) |
| ③ 원본 훼손 | **2중 사본 + 격리 인스턴스 + 스텝별 체크포인트**: 원본은 절대 열지 않고 세션별 작업사본만 연다(모든 닫기는 SaveChanges:=False). 전체실행은 별도의 숨김 Excel 인스턴스에서 원본 기준(pristine)으로 다시 계산하고, 성공 시에만 결과를 반영한다. 각 스텝 실행 직전 상태를 스냅샷으로 영속화해, 실패 시 실패 지점 직전으로 복원하고 그 지점부터만 이어 실행한다. (도 4, 구성 200) |
| ④ LLM 불확실성 | **적용 게이트 + 단방향 엔진 전환 + 제약 흡수 계층**: 적용 직전 정적 게이트가 코드를 검사해 언어별 한계(예: 과다 읽기)는 재생성 없이 이종 엔진(VBA)으로 즉시 전환하고, 전환 산출물에는 게이트 우회 표지를 부여해 두 엔진이 서로 되튕기는 무한 루프를 상태기계 수준에서 차단한다. 또한 시트명 31자 절단, CSV 시트명 파생 등 애플리케이션 고유 제약을 이름 해석 폴백 사다리(7단, 유일 매칭 시에만 완화)와 쓰기측 절단 정책으로 대칭 흡수한다. |
| ⑤ 요구 불투명 | **휴먼-인-더-루프 매핑 UI**: 추출된 요구를 파일 단위 행으로 접어 [요구 시트]↔[실제 시트] 페어로 제시하고, 해결 경위를 '정확 매칭/AI 자동매칭/사용자 확인 완료'로 구분 표시하며, 미해결 항목이 있으면 실행 진입 자체를 차단한다. |
| ⑥ 수작업 단절 | **무후킹 복붙 캡처**: 키보드 후킹 없이, 스프레드시트가 클립보드에 남기는 전용 포맷(Link)에서 소스(북/시트/범위)를, 세션 워크북 창의 선택 상태(RangeSelection)에서 대상(붙여넣은 위치)을 사후 역추적해 좌표 기반 결정적 재생 스텝으로 변환·저장한다. (도 5) |
| ⑦ 교차파일 미지원 | **전 계층 (워크북, 시트) 2원 키 설계**: 스킬 코드가 `book("A")`/`src_book`/`dst_book` 으로 파일을 명시하고, 격리 실행기는 재계산 대상은 원본 사본으로·교차참조 문서는 현재상태 동반본(SaveCopyAs)으로 **한 인스턴스에 함께 개방**해 `Workbooks("다른파일")` 참조를 성립시킨다. 캡처(교차파일 복붙의 클립보드 소실 폴백), 매핑(시트 소유자 검증으로 오귀속 방지), 되돌리기(교차 쓰기 목적지까지 리셋 집합에 포함) 전 계층이 교차파일을 1급 개념으로 다룬다. |
| ⑧ 자원 의존 | **저사양 1급 지원 설계**: 실행 주체가 로컬의 기설치 Excel 이고 LLM 연산은 외부 API 로 위임되므로 로컬 부담이 없다. 전체실행은 그룹당 인스턴스 생성+동기화(N콜) 대신 **격리 인스턴스 1개·HTTP 1콜** 배치로 재편해 저사양 PC 의 멈춤 원인을 구조적으로 제거했고, 진행률을 실행 락 밖 무락 채널로 분리+타임아웃을 내부<외곽<클라이언트로 서열화해 느린 HDD·저속 CPU 에서 '오래 걸리는 정상 작업'이 거짓 실패로 잘리지 않는다. 실측: 4코어 CPU·12GB RAM·HDD 사무용 PC 에서 수십 스텝·수십만 행 절차 완주. |
| ⑨ 포맷·버전 한계 | **자체 파서 부재(위임형 호환성)**: 파일을 직접 파싱하지 않고 **사용자 PC 에 설치된 Excel 을 COM 으로 구동**하므로, 그 Excel 이 열 수 있는 모든 확장자(.xls/.xlsx/.xlsm/.xlsb/.csv/.tsv 등)와 버전을 그대로 지원하고 서식·수식·피벗이 보존된다. 확장자 위장 파일은 시그니처 판별→올바른 확장자 임시 사본(해시 고정 이름) 변환으로, CSV 의 단일시트 제약은 다중시트化 시 xlsx 자동 승격으로 흡수한다. |

### 3-2. 기타 본 발명으로 인한 효과

- **교차파일 절차의 저장·재사용**: "A 파일에서 집계→B 파일에 기입" 같은 다중 워크북 횡단 절차를
  스킬로 저장하고, 다음 회차에 **파일 세트를 통째로 교체**해 재실행할 수 있다 — 발명자가 인지하는
  공지기술 중 이를 지원하는 것은 없다.
- **극한 저사양 구동**: 4코어급 CPU·12GB RAM·HDD 의 사무용 최저사양 PC 에서 수십 스텝·수십만 행
  절차를 완주한다(실측). 격리 인스턴스 1개·1콜 배치, 무락 진행률, 타임아웃 서열화, LLM 연산의 외부
  위임이 결합된 구조적 결과로, 클라우드·고사양 장비 도입 없이 기존 PC 그대로 배치 가능하다.
- **전 포맷·전 버전 호환**: 자체 파서 없이 설치된 Excel 을 구동하므로, Excel 로 열리는 모든 시트
  확장자(.xls/.xlsx/.xlsm/.xlsb/.csv/.tsv, 확장자 위장 파일 포함)와 Excel 버전에 대응하며
  서식·수식·피벗테이블이 변환 손실 없이 보존된다.
- **회차 반복 업무의 무인화**: 월 단위 정산에서 파일 교체만으로 수십 스텝 절차가 재실행된다(파일명·시트명 변형 자동 흡수).
- **실패 내성**: 실패한 실행조차 스텝별 스냅샷을 남겨 이후 복구 비용을 줄인다(실패 예외 페이로드에 체크포인트 동봉).
- **절차 수준 조작성**: 절차가 스텝 파이프라인 + 스텝별 스냅샷으로 구조화된 파생 효과로, 단계 단위
  켜고 끄기(on/off), 단계 단위 undo/redo, 수정·실패 지점 직전 상태로의 복원 후 부분 이어실행이
  가능하다 — 라이브 문서를 직접 변형만 하는 대화형 도구((사) 등)에는 없는 조작 모델이다.
- **대용량 안정성**: 진행률 채널을 실행 직렬화 락 밖의 무락(lock-free) 공유 구조로 분리하고 타임아웃을 내부<외곽<클라이언트로 서열화해, 수십만 행 작업도 거짓 실패 없이 완주한다.
- **원격(VDI) 환경 적응**: 원격 채널의 마우스 이벤트 유실(실측 약 7%)을 눌림-즉시 합성 클릭과 사후 중복 삼킴으로 보상해 조작성을 유지한다.
- **보안 제품 친화**: 전역 입력 후킹·화면 캡처를 쓰지 않으며, 파일 원본이 통째로 외부 서버에
  업로드되지 않는다(실행은 전부 로컬 Excel; LLM 에는 코드 생성에 필요한 구조 정보 위주로 전달) —
  기업 보안 에이전트 환경과의 충돌면이 작다.

#### 구성요소 설명

**(100) 네이티브 셸** — WebView2를 담는 최상위 창. (110)은 명명 뮤텍스로 이중 실행(→고아 Excel)을
차단하고 서버 프로세스 사망 시 시간창 내 횟수 제한 자동재시작을 수행한다. (120)은 Excel 표시 패널의
스크린 좌표를 웹 페이지 전역객체로 주입해 3개 프로세스(C#/JS/Python)가 하나의 좌표계를 공유하게 한다.
(130)은 "WebView2가 비활성→활성 전환의 첫 클릭을 소실"하는 플랫폼 특성과 "소유창 활성 중 작업표시줄
클릭=최소화" OS 기본동작을 각각 선제 포커스와 WndProc 치환으로 상쇄한다. (140)은 장시간 COM 작업 중
사용자 끼어들기를 막되, 잠금 범위를 '오버레이 영역과의 기하학적 교차'로 한정해 같은 PC의 무관한 Excel
창은 건드리지 않는다.

**(200) 로컬 실행 서버** — (210)은 업로드 원본을 절대 열지 않고 세션별 고유 폴더에 **원본과 동일한
파일명**의 작업사본을 만들어 연다(동일 파일명 유지로 코드의 `Workbooks("이름")` 참조가 성립). 모든
닫기는 SaveChanges:=False이므로 어떤 비정상 종료 경로에서도 원본이 오염될 수 없다. (211)은 확장자와
실제 내용이 다른 위장 파일(.xls로 위장한 HTML 등)을 시그니처 검사로 판별해 올바른 확장자의 임시 사본
으로 변환해 열되, **임시 파일명의 앞 31자를 원본 파일명의 해시로 고정**하여(뒤는 난수) 스프레드시트가
파일명에서 파생시키는 시트명이 매 실행 동일하게 재현되게 한다. (220)~(230)은 4-3절, (240)~(250)은
4-2·4-5절에서 상술한다. (260)은 시트 이름 해석 시 정확명→별칭→교차워크북 유일→정규화 유일→휘발성
토큰(월/날짜/버전) 제거 안정키→31자 절단→단일시트의 7단 폴백을 적용하되 **각 단계에서 후보가 유일할
때만** 완화를 허용해 오매칭을 봉인하고, 쓰기측(시트 개명)은 31자 절단을 대칭 적용해 읽기-쓰기 왕복
일관성을 보장한다.

**(300) 라이브 Excel** — 임베딩 방식이 본 발명의 요점 중 하나다. 자식창화(SetParent, WS_CHILD)는
스프레드시트의 셀 클릭·선택 입력 루프를 구조적으로 파괴함이 실측으로 확인되었다. 본 발명은 창을
top-level로 유지한 채 ①캡션/테두리 제거·툴윈도우화 스타일 변형, ②무활성 표시(SW_SHOWNA,
SWP_NOACTIVATE), ③미표시 창의 화면 밖(-32000) 파킹, ④포커스 핸드오프의 조합으로 "앱 안에 박힌
것처럼 보이되 입력은 온전한" 합성을 달성한다.

**(400) 재바인딩 엔진** — 4-4절 상술. **(500) 웹 UI** — 자연어 대화(510)로 스킬을 생성하고,
스텝 파이프라인(520)으로 편집·토글·삭제하며, 실행기(530)에서 저장 스킬을 새 파일에 매핑·일괄 실행
한다. (540)은 적용 직전 정적 검사와 단방향 엔진 전환(Python→VBA→원본 Python 강제, 복구 산출물은
게이트 우회 표지)을 수행한다. (560)은 원격 환경의 mouseup 유실을 눌림-즉시 합성 클릭 + 진짜 이벤트
사후 삼킴(대기목록 매칭)으로 보상하며 더블클릭 의미(두 번 눌림 감지→합성 dblclick)까지 보존한다.

### 4-3. 무손실 격리 전체실행·복구 (도 4 — 핵심 방법 1)

```
[도 4] 격리 배치 전체실행 + 체크포인트 복구
 S301 클라이언트: 연속 같은-파일 스텝을 그룹으로 묶고
      리셋 대상 = 실행 대상 ∪ 교차참조 파일 집합을 계산, 1콜 전송
   ▼
 S302 서버: 숨김 격리 Excel 인스턴스 1개 기동(DispatchEx)
      ├─ 리셋 대상: 업로드 원본(sourcePath)의 임시 사본을 '원본 파일명 그대로' 오픈  ← pristine
      └─ 그 외 교차참조: 라이브 현재 상태의 SaveCopyAs 동반본 오픈
   ▼
 S303 스텝 루프: [스텝 직전 SaveCopyAs 스냅샷 → 실행(Python COM/VBA 주입)]
      진행률은 락 밖 공유 dict 에 기록(무락 폴링, 위상: 스텝/동기화/저장)
   ▼
 S304 성공: 변경 파일만(wb.Saved 판정) 결과 반영
      ├─ 생성기(sync): 라이브 세션에 파일당 1회 통째 반영
      └─ 실행기(file): 라이브 무접촉, 결과를 출력 폴더 파일로 저장(CSV 다중시트→xlsx 승격)
   ▼
 S305 실패: 라이브 반영 '전에' 예외 → 라이브 무손상.
      예외 페이로드에 실패 스텝 직전까지의 스냅샷 목록 동봉
   ▼
 S306 자동복구 루프(전체 3회·스텝당 2회 상한):
      실패 분류 게이트(환경 오류·의존 시트 누락·행위 캡처 스텝·기검증 스킬 → 재생성 금지)
      → 통과 시: 세션별 최초 스냅샷 1개씩만 복원(파일 수와 무관하게 최소 복원)
      → 실패 스텝 재생성(로컬 규칙 우선, LLM 차선; 언어 전환 정책 적용)
      → 실패 지점부터만 이어 실행(skipReset), 스냅샷 없으면 pristine 전체 재실행 폴백
```

단계 설명: S302의 이중 오픈 정책(pristine vs 동반본)이 "항상 원본부터 재계산"과 "교차파일 참조
성립"을 동시에 만족시키고, S303의 사전 스냅샷과 S305의 예외 동봉이 "실패가 복구 자산을 남기는"
구조를 만든다. S306의 분류 게이트는 코드 재생성으로 고칠 수 없는 실패(환경·사용자 행위 재현·기검증)
를 루프 앞단에서 걸러 무의미한 LLM 호출을 배제한다.

여기서 스텝별 스냅샷은 단순한 파일 백업이 아니라 **"실행 시점의 스프레드시트 상태(라이브 COM
인스턴스에 반영된 값·수식·서식·시트 구성)를 논리적으로 복제한 비일시적 데이터 저장체"**로 정의되며
(기능적 정의 — 저장 수단이 SaveCopyAs 파일이든 다른 직렬화 형태든 권리범위에 포섭), 실패 시 예외
페이로드에 동봉된 스냅샷 식별자 목록을 분석해 "어느 세션이 어느 스텝 직전 상태까지 보존돼 있는지"를
역추적하여 최소 복원 집합을 결정한다.

#### 4-3-1. 실패 분류 기준·예외 페이로드·엔진 전환 임계치 (실시예 — 제33조 뒷받침 보강)

**(A) '환경 오류'(재생성 금지) vs '복구 가능 오류'의 판별 기준** — S306 분류 게이트의 구체 규칙:

| 분류 | 판별 근거(실시예) | 처리 |
|---|---|---|
| 환경 오류 | 오류 문언이 매크로 보안 차단 패턴("매크로를 실행할 수 없습니다", "macros may be disabled" 등 정규식)과 일치 — 코드를 다시 생성해도 동일 실패 | 재생성 금지, 즉시 보고(환경 설정 안내) |
| 의존 시트 누락 | 실패 원인이 "선행 스텝이 만들었어야 할 중간 시트의 부재"로 판정(대화 이력의 시트 생성 후보와 대조) | 재생성 금지, 해당 시트를 만드는 스킬의 '삽입'을 사용자에게 제안 |
| 행위 캡처 스텝 | 스텝 코드에 행위 캡처 표지(`[복붙 캡처]`)가 존재 — 사용자가 실제로 한 동작의 좌표 재생이므로 LLM 재생성 시 의미가 훼손됨 | 재생성 금지, 그대로 보고 |
| 기검증 스킬 | 스텝에 기검증 표지(trustedStatic)가 존재 — 저장 시점에 이미 실행 검증된 코드 | 정적 게이트 재생성 생략, 저장 코드 그대로 실행 |
| 복구 가능 | 상기 어디에도 해당하지 않는 런타임 실패 | 체크포인트 복원 → 재생성(스텝당 2회·전체 3회 상한) → 실패 지점부터 이어 실행 |

**(B) 예외 페이로드에 동봉되는 스냅샷의 구체 포맷** (실측 JSON 구조):

```json
{ "errorInfo": {
    "stepIdx": 7, "stepId": "u1kr47qu", "message": "...", "cause": "...",
    "stepSnapshots": [
      { "excelId": "<세션 식별자>", "stepIdx": 0, "stepId": "<스텝 식별자>",
        "downloadId": "<스냅샷 저장체 식별자>",
        "downloadUrl": "/api/workbooks/download/<식별자>",
        "name": "prestep_<해시>_<원본파일명>.xlsx" } ],
    "failStateSnapshots": [
      { "excelId": "<세션 식별자>", "downloadId": "<실패 시점 상태 저장체>" } ] } }
```

`stepSnapshots`는 각 스텝 '직전' 상태(체크포인트 이어실행용), `failStateSnapshots`는 실패 '시점'의
관여 파일 전체 상태(다중 파일 일괄 복원용)로 용도가 구분되며, 세션 식별자(excelId)로 "어느 문서의
어느 시점"인지 역추적한다.

**(C) 단방향 엔진 전환(Python→VBA)의 트리거·임계치** (실시예):

1. **정적 검출 전환**: 적용 전 AST/패턴 검사에서 "다중 토큰 분해 + 키 매칭 + 합산 + 쓰기"의 조합
   패턴이 검출되면(저사양 PC 에서 COM 왕복 폭증으로 멈춤이 실측된 작업 부류) 재생성 없이 VBA 로
   즉시 전환한다.
2. **런타임 예산 전환**: COM 호출 예산(기본 400회, 설정 가능) 초과, 읽기 범위 셀 수 상한(설정 시)
   초과, 실행 데드라인(설정 시; 무한 루프는 트레이서가 감시) 초과 시 해당 스텝을 VBA 재생성 대상
   으로 분류한다.
3. **역방향 진동 차단**: VBA 실패로 Python 복구본을 만들 때는 산출물에 게이트 우회 표지
   (trustedStatic)와 데드라인 확장 표지(extendedTimeout)를 부여해, 정적 게이트가 이를 다시 VBA 로
   되돌리는 무한 진동을 상태기계 수준에서 차단한다(단방향성의 구현 근거).

```

   ├─ 자연어 멘션: @시트[파일/시트] 등
   ├─ 저장 메타: targetFileId + targetSheetName (교차파일 소유자 검증 통과 시)

   ▼

   ▼
 S404 휴먼-인-더-루프 UI: 파일별 1행, [요구 시트]↔[실제 시트] 페어,

   실제 이름으로 전역 치환한 '매핑본' 파이프라인 생성 → 실행 동안만 교체,
```

단계 설명: S402가 본 방법의 안전핀이다. "입력으로 요구되는 시트"와 "실행이 만들어내는 시트"를
정적으로 분리하지 못하면, 생성물 이름이 실제 시트명으로 치환되어 코드가 파괴되거나(치환 폭주),
존재하지 않는 시트가 필수 업로드로 요구되어 실행이 차단된다(요구 과잉). 이를 위해 VBA의 대입/비교
문맥 라인 판별과 Python의 변수-인자 리터럴 역추적을 결합했다. S405의 "실행 시 한정 치환"은 저장
스킬을 회차 불변의 원형으로 보존해, 같은 스킬을 매월 다른 파일에 반복 재바인딩할 수 있게 한다.

## 5. 보호받고자 하는 사항 (기술의 핵심)

### [핵심 1] 저장 스킬의 이종 문서 재바인딩 방법 (한국 특허 청구항 스타일 — 변리사 검토 반영판)

> 검토 의견 반영: '생성물(작업 중 추가된 시트)을 요구 목록에서 제외'하는 로직은 단순 유사도 매칭과의
> 차별점이므로 **독립항의 필수 구성요소**로 명시한다(단순 "파일명/시트명 검색 + LLM 문자열 치환"
> 조합이라는 거절 논거의 방어선).

**청구항 1 (독립항, 방법)**: 컴퓨터로 구현되는 스프레드시트 자동화 스킬의 재바인딩 방법으로서,
저장된 스킬의 코드 및 메타데이터를 정적 분석하여 상기 스킬 실행에 필요한 워크북 및 시트 요구
집합을 추출하는 단계;
상기 코드 내의 시트 추가, 개명 또는 복사 연산에 대응되는 인라인 리터럴 인자 및 변수 대입문을
추적하여, 상기 스킬 실행 과정에서 생성되는 생성물 시트를 상기 요구 집합에서 제외하는 단계;
상기 요구 집합을 신규 문서 집합과 다단계 유사도 규칙에 기반하여 자동 매칭하는 단계; 및
실행 직전에 상기 매칭 결과에 따라 코드 내 리터럴을 치환한 매핑본을 생성하여 실행하고, 실행 종료
후 상기 원본 스킬의 상태를 유지하는 단계를 포함하는, 방법.

**청구항 2 (종속항)**: 제1항에 있어서, 상기 생성물 시트를 제외하는 단계는 비교 문맥 라인과 연산
문맥 라인을 구분하여 비교 문맥 라인은 생성물 판정에서 배제하는, 방법.

**청구항 3 (종속항)**: 제1항에 있어서, 상기 자동 매칭하는 단계는 다단계 유사도 규칙으로
[정확→정규화→어간→포함→토큰 적중률]을 순차 적용하고, 각 단계에서 유일 일치가 확인될 때만 매칭을
확정하는, 방법.

**청구항 4 (종속항)**: 제1항에 있어서, 상기 방법은 다중 워크북을 횡단하는 참조 구조를 지원하며,
파일 세트 교체 시 매칭된 워크북의 소유자를 검증하여 재바인딩하는, 방법.

- 추가 종속항 소재: 요구 소스 4계열(리터럴 쌍/자연어 멘션/저장 메타/행위 캡처 인자)의 통합;
  스텝 순서 누적에 의한 선행 생성물 제외; 미해결 요구 존재 시 실행 진입 차단; 매핑 상태의 3분류
  표시(자동 정확/자동 유사/사용자 확정)와 2단 실행 진입; 변수 인자의 단독 대입문 리터럴 역추적.

### [핵심 2] 라이브 스프레드시트 무손실 격리 실행 방법

**독립항 후보 B (방법)**: (a) 원본 문서를 개봉하지 않고 세션별 작업사본(원본과 동일 파일명)만 라이브
인스턴스에 개방하는 단계; (b) 일괄 실행 요청 시 별도의 은닉 인스턴스에서, 재계산 대상은 원본 사본으로,
교차참조 문서는 현재 상태 사본으로 개방하는 단계; (c) 각 스텝 실행 직전에 **실행 시점의 스프레드시트
상태를 논리적으로 복제한 비일시적 데이터 저장체**(스냅샷)를 생성·영속화하고, 실행 실패 시 스냅샷
식별자 목록을 오류 응답에 동봉하는 단계; (d) 전 스텝 성공 시에만 변경 문서를 라이브 세션 또는
출력 파일로 반영하고, 실패 시 라이브를 무변경으로 유지하는 단계; (e) 실패 스텝을 복구 가능성 기준으로
분류한 뒤, 동봉된 스냅샷의 세션·시점 정보를 역추적하여 세션별 최초 스냅샷만 복원하고 실패 지점부터
이어 실행하는 단계를 포함하는 방법.

> 방어 논거(변리사 검토 반영): 일반 RPA/DB 의 '체크포인트 재시작'과의 차별은 ①스냅샷이 **라이브
> COM 인스턴스와의 연동 상태**(값·수식·서식·시트 구성·교차참조 동반본)를 복제한다는 점, ②실패
> 예외에 스냅샷 식별자를 동봉해 **오류 응답 자체가 복구 자산**이 된다는 점, ③복원이 파일 수와
> 무관한 '세션별 최소 집합'으로 결정된다는 점이다. 청구항에 이 세 요소를 명시한다.

- 종속항 소재: 재생성 금지 분류(환경 오류/행위 캡처 스텝/기검증 스킬); 단방향 엔진 전환 사다리와 복구
  산출물의 게이트 우회 표지(진동 차단); 무락 진행률 채널과 실행 위상 보고; 타임아웃의 계층 서열화;
  위장 포맷 파일의 해시 고정 임시명 변환 개방(시트명 재현성+동시 개방 유일성);
  **격리 인스턴스 1개·단일 요청 배치 구조에 의한 저사양(4코어/12GB/HDD급) 장치에서의 완주 보장**;
  **자체 파서 없이 기설치 스프레드시트 애플리케이션을 구동함으로써 그 애플리케이션이 개방 가능한
  전 확장자·전 버전 문서를 지원 범위로 흡수하는 위임형 호환 구조**.

### [핵심 3] 무후킹 사용자 행위 캡처 방법

**독립항 후보 C (방법)**: 전역 입력 후킹 없이, (a) 클립보드의 스프레드시트 전용 포맷(Link)에서 복사
소스의 북/시트/범위를 파싱하고, 소스 소실 시 복사 모드 활성 중 주기 스냅샷으로 폴백하는 단계; (b) 전역
선택이 아닌 세션 문서 자체 창의 선택 상태로 붙여넣기 대상을 판정하는 단계; (c) 검증(다중영역 거부,
크기 비교, 교차파일 판정) 후 좌표 기반 결정적 재생 명령으로 변환·저장하는 단계; (d) 재생 시 부재
소스 문서를 이름 정규화 역조회로 자동 개방하는 단계를 포함하는 방법.

> 방어 논거(변리사 검토 반영): 원격 제어 소프트웨어의 이벤트 유실 보정(전송 채널 계층의 재전송·보간)
> 과 달리, 본 발명의 행위 복원은 **애플리케이션 계층의 의미 상태** — 문서 내 셀 선택 상태
> (RangeSelection)와 클립보드에 남은 스프레드시트 전용 데이터 — 를 매칭하여 유실된 이벤트의 '의도'를
> 논리적으로 재구성한다. VDI 전용 기술이 아니라 로컬 환경에서도 동일하게 동작하는 일반 방법으로
> 청구한다. (클릭 복구기(560)도 동일 논거: 채널 보정이 아니라 '눌림 관측→의미 복원→진짜 이벤트
> 사후 중복 제거'의 애플리케이션 계층 상태기계다.)

### [핵심 4] 라이브 애플리케이션 오버레이 합성 구조 (장치항 소재)

top-level 유지 + 스타일 변형 + 무활성 배치(SW_SHOWNA/SWP_NOACTIVATE) + 화면 밖 파킹 + 포커스
핸드오프 + 3자(네이티브 셸/웹뷰/실행 서버) 좌표 동기 브리지 + 기하학적 교차 한정 입력 잠금 +
원격 입력 유실 보상(눌림-즉시 합성/사후 삼킴)의 조합.

> 기능적 정의(회피설계 방지 — 변리사 검토 반영): 청구항에서는 API 명칭 대신 **"애플리케이션의
> 프로세스 경계를 넘어선 윈도우 스타일 제어 및 무활성 배치에 의한 레이아웃 합성 기술"**로 정의한다.
> 같은 취지로, 위장 확장자 처리(211)는 **"파일 시스템의 확장자 정보와 무관하게 파일 시그니처에
> 기반하여 판별하고, 원본 식별자로부터 결정적으로 파생되는 가상 파일명을 부여하여 재현성을 보장하는
> 호환 개방 기술"**로, 스텝 스냅샷은 **"실행 시점의 스프레드시트 상태를 논리적으로 복제한 비일시적
> 데이터 저장체"**로 각각 기능적으로 정의한다.
